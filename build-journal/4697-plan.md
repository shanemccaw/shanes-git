# Plan — #4697: move_to_status enum cleanup, add/remove-label tools, close_issue terminal-label strip

Tracking issue: `shanemccaw/Shane-McCaw-MSP#4697` (sub-issue of Feature #4692).
Real work: this repo (`shanemccaw/shanes-git`, the live GitHub MCP server). Written before any code change per #4307.

## Problem Description

Three real gaps in the live MCP server's write tools, all surfaced by the #4692 label/board simplification:

1. **`move_to_status` still accepts `"Done"`.** Per Shane's 2026-09-18 design session (#4692), board columns collapse to four pure human-gate columns — Backlog, Batter Up, AI Batter Up, Ask Shane. Real GitHub issue *close* is the terminal state; there is no "Done" board column in the architecture anymore. The tool's enum still offers `"Done"` (`src/tools/move-to-status.ts:34`), so a chat can still move a card there.
2. **`update_issue`'s `labels` param is a full replace and it is dangerous.** Confirmed by #4686: a caller that passes `labels` wipes every other real label (`blocked`, `Shane To-Do`, …) unless it re-sends the entire current set. There is no additive/subtractive label tool, so a chat that wants to add one label must first read all labels and re-send them — the exact footgun #4686 documents.
3. **`close_issue` leaves terminal-state labels behind.** Shane's real intent: a verifying chat's job is "confirm this is real, say close" — not a multi-step manual process of separately stripping stray state labels first. Today `close_issue` (`src/tools/close-issue.ts`) closes the issue and touches no labels, so a closed issue keeps a now-meaningless `blocked` (or legacy `in-flight`/`complete`).

## Root Cause Analysis

- **(1)** `STATUS_OPTION_ID` in `move-to-status.ts` was seeded from #3395's original five-status body (`Batter Up / Backlog / AI Batter Up / Ask Shane / Done`). `ALLOWED_STATUSES` and the tool's `enum` both derive from that record, so `"Done"` propagates automatically. The board vocabulary changed under it (#4692); the code did not. `list_board_column.ts:19` carries a hardcoded copy of the same five-status list — a second, drift-prone source of the same `"Done"`.
- **(2)** `update_issue` maps `args.labels` straight to GitHub's `PATCH /issues/{n}` `labels` field, whose documented semantics are full replacement. There has never been a delta tool; the replace behavior is correct GitHub semantics but the wrong default ergonomics for a chat that just wants to toggle one label.
- **(3)** `closeOneIssue` performs only the NOT_PLANNED-comment enforcement (#2167) and the close itself. Label cleanup was never part of it, so it was left to the caller and routinely skipped.

## User Review Required

Two decisions stated explicitly for Shane's review:

### Decision A — change 3 is UNCONDITIONAL behavior, not a new parameter. Why:

Shane's stated intent is to *remove* a manual step, not add a knob. A parameter defaulting to "strip" would still let a caller accidentally skip it; a parameter defaulting to "don't strip" would preserve the exact manual burden being retired. Critically, there is **no real scenario** where you close an issue and want it to *keep* a `blocked` / `in-flight` / `complete` label — those labels are, by definition, meaningless once the issue is closed (a closed issue cannot be "actively blocked", "in flight", or "awaiting close"). So the correct-behavior set is a fixed, small allowlist and the safe default is: always strip exactly those, never anything else. It is unconditional.

The strip is **allowlist-only** and provably safe: it removes only from `TERMINAL_STATE_LABELS = ["blocked", "in-flight", "complete"]`, reading the issue's real current labels first and issuing a delete only for those actually present. `Shane To-Do`, `bug`, `security`, and every other label are never touched — those are not state labels (per #4697's body and #4692: `Shane To-Do` is explicitly retained as genuinely useful; `bug`/`security` are cross-repo classification, not workflow state).

- `blocked` — the primary, per #4697's verification requirement. `blocked_by` edges remain the authoritative blocking mechanism; the label is a cheap index that is meaningless on a closed issue.
- `in-flight` / `complete` — being retired entirely by the sibling BuildConsole issues (#4693/#4694). Stripping them on close is harmless cleanup of any that legacy issues still carry, and keeps a closed issue from displaying a retired "being worked on / awaiting close" state. If Shane prefers to strip `blocked` only, delete the other two entries from the one `TERMINAL_STATE_LABELS` constant — no other change needed.

### Decision B — also remove `"Done"` from `list_board_column`'s enum (minor scope extension). Why:

`list_board_column.ts` and `move-to-status.ts` share, by the file's own comment, the *identical* "restricted status vocabulary." #4697's letter names only `move_to_status`, but leaving the read tool able to enumerate a `"Done"` column that the architecture (#4692) says no longer exists would (a) create a divergent, drift-prone pair of enums and (b) perpetuate the confusion this Feature retires. Per-issue reads still work via `get_board_status` regardless. If Shane wants the read tool to keep listing a historical "Done" column, revert the one-line enum edit in `list_board_column.ts`.

## Proposed Changes

1. **`src/tools/move-to-status.ts`** — remove the `"Done": "0003ae3b"` entry from `STATUS_OPTION_ID`. `ALLOWED_STATUSES`, the `enum`, the description, and `moveIssueToStatus`'s validation all derive from it, so `move_to_status` will then reject `"Done"` with the existing clear "must be one of: …" error (no silent no-op). `batch_move_to_status` inherits the fix (it calls `moveIssueToStatus`).
2. **`src/tools/list-board-column.ts`** — remove `"Done"` from the hardcoded `ALLOWED_STATUSES` (Decision B).
3. **`src/github.ts`** — add three small helpers on the existing server-side-PAT client:
   - `getIssueLabels(number, repo)` → the issue's real current label names.
   - `addIssueLabel(number, label, repo)` → `POST /issues/{n}/labels` (GitHub's own *additive* semantics — never a replace), returns the resulting full label set.
   - `removeIssueLabel(number, label, repo)` → `DELETE /issues/{n}/labels/{name}`, returns the resulting set; a 404 (label wasn't attached) is treated as a clean no-op, not an error.
4. **`src/tools/labels.ts`** (new) — two new write tools, `add_label` and `remove_label`, each `{ number, label, context, repo? }`. Both **read the issue's current labels first** and only change the delta: `add_label` no-ops (`changed: false`) if the label is already present; `remove_label` no-ops if it is already absent. Both require `context` (#3538) like every write tool. This is purely additive — `update_issue`'s existing full-replace `labels` param is left working unchanged for any caller that deliberately wants a full replace.
5. **`src/tools/close-issue.ts`** — after the successful close, unconditionally strip any present `TERMINAL_STATE_LABELS` (reading current labels first, delete-per-present-label via the github.ts helper). Add the stripped labels to `CloseOneIssueResult` (`strippedLabels: string[]`) so the result proves what happened. `batch_close_issues` inherits it (it calls `closeOneIssue`).
6. **`src/tools/index.ts`** — register `addLabelTool` + `removeLabelTool` in `ALL_TOOLS`.
7. **README.md** — document the two new tools and the close-strip behavior in the tool list, and drop `"Done"` from the documented `move_to_status`/`list_board_column` status set.

No fixture/hardcoded data anywhere; every change operates on real GitHub state via the existing server-side PAT client.
